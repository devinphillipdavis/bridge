# Agent rules for OSIRIS repositories

These rules bind every AI coding agent working in this repository, Antigravity (`agy`)
and Gemini included. They come from Gate 0 of the OSIRIS × Antigravity dual-node plan
(2026-10-10). Where any other file or prompt here (AGENTS.md, CONTRIBUTING.md, a README,
a skill) allows more, these rules win. When a rule blocks you, stop and ask the human;
never work around it.

## You propose; the human commits

Leave a proposed diff in the working tree and stop. The human reviews it and makes every
commit, push, merge, tag and release. Do not run, or get another tool to run:

- `git add`, `git commit` (including `--amend`), `git rebase`, `git merge`, `git cherry-pick`, `git revert`
- `git tag`, or `git push` in any form (`--force` and `--force-with-lease` included)
- `git reset --hard`, `git clean`, `git stash drop`, `git branch -D`, `git worktree add|remove`,
  or a checkout/switch to another branch
- `gh pr create|merge`, `twine upload`, any `--publish` flag, a Zenodo deposit, or any other
  publish or upload step

Reading git state (`git status`, `git diff`, `git log`, `git show`) is fine.

## When the sandbox or a permission blocks you

Stop and ask. Do not try the same thing another way: no alternative command, no other shell,
no script that does it for you, no disabling the sandbox, no editing agent or sandbox settings.
Say what you ran, what blocked it, and what you need.

Do not edit this file or any agent configuration (GEMINI.md, AGENTS.md, `.agent/`, `.gemini/`)
unless the prompt explicitly asks you to.

## Installs, downloads and network

- No package installs without the human's approval in this session: `pip`, `uv`, `pipx`, `apt`,
  `pkg`, `npm`, `cargo`, `go install`, `sdkmanager` or anything similar.
- Never pipe a download into a shell or interpreter (`curl … | bash`, `wget -O- … | sh`).
  An approved installer is saved to a file, checked against a pinned checksum, and shown to the
  human before it runs.
- Tests run offline. Do not write or run tests that reach the network, Ollama, a cloud API or a
  QPU; mock them.
- Do not call IBM Quantum, Vertex or Gemini APIs, Zenodo, Neon, GitHub or any other remote
  service from code you run unless the human starts that run.

## Secrets: never read them

Do not open, print, search, copy, archive or summarize:

- `.env`, `.env.*`, `*.env` (`.env.txt` included)
- `~/.ssh/`, `~/.config/gcloud/`, `~/.config/gh/`, `~/.aws/`, `~/.netrc`, `~/.git-credentials`,
  keyrings, `*.pem`, `*.key`, service-account JSON
- Secret Manager values, `OSIRIS_PG_URL`, or tokens in environment variables (never dump the
  whole environment with `env` or `printenv`)

If a task seems to need a credential, stop and ask. Never put a credential in code, a test, a
fixture, a log, an archive, a context packet or a commit message. Before building any archive
(tar, zip, bundle), exclude `.env*` and run a secret scan: a SHA-256 or extraction check proves
integrity, not secrecy.

## Evidence and claims

- Never write to the canonical genome ledger or promote staged records. You propose; the human
  promotes on Node Beta.
- A signature counts only if it was made with an enrolled node key. Never sign evidence with a
  test seed, a deterministic key or a key you generated.
- You cannot mark a value, threshold or claim "verified", and you do not add or change
  thresholds. Run nothing gated on Γ unattended: Γ ≤ 0.092 (mesh policy) and Γ = 0.95
  (policy.json v3) are not yet one registered definition.
- A description of what code does is a claim until a test shows it. Cite the test, or say there
  is none.
- Do not use the NotebookLM "Osiris Staging Runtime" report as input. τ₀ ≈ 46 μs,
  θ_lock = 51.843° and Φ = 0.7734 are refuted or artifacts in the claims register; never present
  them as verified or as design limits.

## How a session runs

1. Work only in the worktree and branch you were started in (`osiris/candidate/<id>` on Node
   Beta, `node/alpha/<topic>` on Node Alpha). One agent per worktree: if you find changes you did
   not make, stop and ask.
2. Touch only the files the prompt allows. The first pass is read-only; stop for approval before
   writing.
3. Keep diffs small and stop at checkpoints, so the work survives a model or credit cutoff.
4. No training runs, sweeps or other long jobs without approval, and nothing longer than the
   node's horizon (300 s on Node Alpha, 1800 s on Node Beta). Heavy runs get the machine to
   themselves.
5. Use repo-relative paths. Never hard-code `/root/…` or `/home/enki/…`.
6. Before handing back, run the repo's offline suite (normally
   `pytest -o cache_dir=/tmp/osiris_pytest_cache tests/`) and `git diff --check`, and report both
   results verbatim.
7. Hand back the diff summary, the test output and anything you could not do. Then stop.
